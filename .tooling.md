# brayness-webspace tooling (curated)

Hosted sessions in two halves that do not mix:

- `control/` - Node. Makes hosts exist, puts code on them, takes them away.
  Talks to the live side only over its HTTP API.
- `src/orchestrator/` - Python3 stdlib. The live code: runs on the host, owns
  sessions. Start it, poll its health, call its API. Nothing else.
- `scripts/` - bash. Root syscalls on the guest and the host: mkfs, mount,
  iptables, chroot, systemd. Called by `control/`, never by hand except to
  debug a step.

No package manager at the project root; `control/` has no dependencies.

## Commands

Run from `work/brayness-webspace/control` (or `npm run webspace -- <args>`).
The environment is the first word and is required.

```
node bin/webspace.js dev  setup              # once: Lima guest, artifacts, boot check
node bin/webspace.js dev  build              # stage the harness, build the template
node bin/webspace.js dev  up [--fresh]       # volume + TAP + API; waits for the seed
node bin/webspace.js dev  stop
node bin/webspace.js dev  restart [--fresh]

node bin/webspace.js prod host up <name> [--smoke]        # ~3 min, ends serving
node bin/webspace.js prod host restart <name>             # push code, re-serve
node bin/webspace.js prod host down <name>                # park, disks kept
node bin/webspace.js prod host down <name> --delete       # drain, then delete
node bin/webspace.js prod host down <name> --delete --no-drain
node bin/webspace.js prod host drain <name> [--delete]    # export and ship only
node bin/webspace.js prod probe [<type>:<zone> ...]       # what can be created now
```

Config is `control/webspace.config.js`: one block per environment (`dev` is
Lima on this Mac, `prod` is GCP). `probe` exits non-zero when nothing can be
made, so it is usable as a check.

## Internals, called by control

`guest-setup.sh`, `boot-check.sh`, `harness-stage.sh`, `template-build.sh`,
`net-up.sh`, `net-down.sh`, `host-bootstrap.sh`, `host-smoke.sh`,
`sessions-volume.sh`, `idle-guard.sh`, `orchestrator-restart.sh`,
`dev-stack.sh`.

Run on a host by hand: `brayness-login.sh` (one ssh login becomes one session).
Clients: `pty-attach.py`, `vsock-exec.py`.

## Tests

`cd control && npm test` - the boundary check. It fails if `src/orchestrator/`
refers to `control/`, or if `control/` reaches into the package instead of
using the API. Proven by breaking the rule and watching it fail.

## Checks (archived)

Every per-node check script (`f3-verify.sh`, `r3a`-`r9`, `a1`, `a2`, `x1`, ...)
and its runs are in `artifacts/firecracker/webspace-archive/`. The eight Mac
operator scripts that `control/` replaces are in
`artifacts/firecracker/webspace-control-port/`. The counts and gotchas behind
each are in `README.md`.

## A session builds and publishes a site (a1, a2)

- The builder is `site/` (`build.mjs`, comark + shiki pinned in its
  `package.json`). Its deps were installed into the image by `template-build.sh`
  while it was still the harness skill `skills/webspace/`; it is not staged
  into the image any more, so a rebuild needs `template-build.sh` updated to
  install it from here.
- Publish is `POST /v1/sessions/{id}/publish {"path": "/root/site"}`; the site
  is served at `/s/{id}/`, and in the dev loop that is
  `http://127.0.0.1:18080/s/{id}/`.
- The a1/a2 checks are in the archive and need a running API: `webspace dev up`.
- A rebuilt template needs a rebuilt seed: `webspace dev up --fresh`.
